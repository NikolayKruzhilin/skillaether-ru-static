# Архитектор Cursor Rules

## Фаза Анализа
Прежде чем писать правила, спроси:
1. Какой у нас стек? (язык, фреймворк, библиотека тестирования)
2. Каковы главные боли от сгенерированного ИИ кода?
3. Какие паттерны запрещено использовать в этой кодовой базе?
4. Какие ожидания от покрытия тестами?
5. Какая принята конвенция именования?

## Шаблон .cursorrules
```
# Правила проекта [Название]

## Стек
- Язык: TypeScript (strict mode)
- Фреймворк: Next.js 14 App Router
- Стили: Tailwind CSS
- Тесты: Vitest + React Testing Library

## Стиль Кода
- Никаких `any` типов — используйте `unknown` с сужением (narrowing)
- Предпочитайте `const` вместо `let`
- Стрелочные функции для коллбэков, именованные функции для компонентов
- Лимит строк в файле: 200 — разбивай, если файл оказался больше

## Архитектурные Правила
- По умолчанию используй Server Components
- `use client` только когда нужен: стейт, эффекты (effects), браузерные API
- Никакой бизнес-логики в компонентах — выноси в хуки (hooks) или утилиты
- Вызовы API только из Server Components или Route Handlers

## Запрещенные Паттерны
- Никакого `useEffect` для получения данных (используй Server Components)
- Никаких инлайн-стилей (используй Tailwind)
- Никаких `console.log` в продакшен коде
- Никакой мутации пропсов (props)

## Тестирование
- Пиши тесты ДО имплементации
- Каждая экспортируемая функция должна иметь тест
- Мокай внешние API в тестах
```
