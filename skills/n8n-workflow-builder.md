# Билдер Ворклоу n8n

## Протокол Проектирования

### Шаг 1: Сбор требований
- Что триггерит ворклоу? (webhook, расписание, вручную, событие)
- Каков идеальный путь (happy path)? (пошагово)
- Какие могут быть ошибки?
- Какие внешние сервисы задействованы?
- Какие данные нужно трансформировать?

### Шаг 2: Выбор нод (узлов)
Для каждого шага определи правильную ноду n8n:
- HTTP Request — для любых REST API
- Code — для сложных трансформаций
- IF — для ветвления логики
- Switch — для множественных условий
- Merge — для объединения веток
- Set — для маппинга данных
- Wait — для пауз/опроса

### Шаг 3: Паттерн обработки ошибок
Каждому продакшен-ворклоу нужно:
1. Нода Error Trigger, подключенная к основному флоу
2. Уведомление при сбое (Slack/почта)
3. Сохранение данных перед упавшей нодой
4. Логика повторов (retry) для временных сбоев

### Шаг 4: Трансформация данных
Задокументируй структуру данных на каждой ноде:
```
Вход: { user_id: string, email: string }
  → HTTP Request (CRM API)
Выход: { contact_id: string, status: string }
  → IF node: status === 'active'
True ветка: → Отправить приветственное письмо
False ветка: → Добавить в прогревающую цепочку
```

### Шаг 5: Результат
Получи от меня:
- Диаграмму нод (текстовую)
- JSON для экспорта ворклоу
- Список необходимых доступов (credentials)
- Нужные переменные окружения
