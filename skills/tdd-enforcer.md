# TDD Enforcer

## Железные Правила
1. НИКОГДА не пиши код реализации без падающего теста
2. Пиши МИНИМУМ кода, чтобы тест прошел
3. Рефактори только тогда, когда все тесты горят зеленым
4. Покрытие должно быть выше 80% до завершения задачи

## Протокол действия

### Шаг 1: RED (Красный) — Пишем падающий тест
- Проанализируй требование
- Напиши тест, описывающий желаемое поведение
- Запусти тест — убедись, что он ПАДАЕТ
- Если он прошел — значит, тест написан неверно или фича уже реализована

### Шаг 2: GREEN (Зеленый) — Минимальная реализация
- Напиши самый простой код, при котором тест проходит
- Никакой оптимизации, никаких сложных структур и красоты
- Запусти все тесты — убедись, что ВСЕ они проходят
- Если что-то упало — чини, прежде чем идти дальше

### Шаг 3: REFACTOR (Рефакторинг) — Приборка
- Улучши качество кода (имена, структура, DRY)
- Запускай тесты после каждого микро-изменения
- Если тест упал — откати последнее действие
- Продолжай, пока код не станет идеально чистым

### Шаг 4: ПОВТОР
- Переходи к следующему тест-кейсу или краевому случаю
- Прогоняй весь тестовый набор после каждого цикла

## Контроль покрытия
По завершении работы над фичей:
1. Запусти инструмент замера покрытия (jest --coverage, pytest --cov и т.д.)
2. Если покрытие < 80%: найди неохваченные ветки кода
3. Допиши тесты для этих путей
4. НЕ ПЕРЕХОДИ к следующей фиче, пока порог в 80% не будет пройден

## Когда НЕ использовать
- Быстрое прототипирование / 'код в мусорку'
- Исследовательские сессии кодинга
- Сложная UI-анимация и визуал (трудно покрыть юнит-тестами)
